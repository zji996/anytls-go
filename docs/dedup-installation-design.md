# 去重解码端安装与迁移

状态：已实现默认安装、开关、旧版 bootstrap 迁移和双服务事务回滚。本地验证记录见 [当前状态](./status.md)；生产服务器更新与客户端业务验收由操作者执行。

## 使用方式

去重解码端作为默认组件，按推荐配置安装并启用，随主服务一起维护。新装和没有保存去重设置的旧版本升级都无需增加参数；用户不需要手写 systemd unit、选择内部端口或修改主服务启动参数。明确关闭过的安装保留关闭状态。

服务器默认提供解码能力，实际使用仍取决于客户端前端的设备名单、域名和 CA 信任。安装器不自动扩大路由器当前的灰度范围；普通 AnyTLS 客户端继续使用原来的连接方式。

新服务器通过新版 bootstrap 安装：

```bash
curl -fsSL https://raw.githubusercontent.com/zji996/anytls-go/zji-dev/scripts/bootstrap-anytls-server.sh \
  | sudo bash -s -- install --non-interactive
```

已有服务器通过新版 bootstrap 升级并启用：

```bash
curl -fsSL https://raw.githubusercontent.com/zji996/anytls-go/zji-dev/scripts/bootstrap-anytls-server.sh \
  | sudo bash -s -- update --non-interactive --no-firewall
```

第二条适用于已有旧版主程序的服务器：同时升级主程序并安装解码端。执行前应确认远端分支包含本文对应实现，源码工作区干净且没有分叉。

安装器已更新后，可以直接调用本机入口：

```bash
sudo bash /opt/anytls-go/scripts/install-anytls-server.sh update --non-interactive
```

后续普通 `update` 沿用已保存的组件状态及参数，并将主程序和解码程序更新到同一源码提交。以前主动关闭过、现在要重新启用时才需要 `--with-dedup`。

显式关闭：

```bash
sudo bash /opt/anytls-go/scripts/install-anytls-server.sh update --without-dedup --non-interactive
```

关闭会撤销主服务接入，再停止并禁用解码服务，保留配置和程序以便再次启用；完整 `uninstall` 才删除受管组件文件。

交互向导提供“安装去重解码端（推荐）”一项：新装和没有保存状态的旧版默认是，已有状态显示保存值。旧版升级在切换前明确显示新增解码服务、资源上限和关闭方式；非交互升级采用同样默认值并输出摘要。提供开启、关闭的管理菜单，复用同一事务，不另写一套安装逻辑。

## 选项与状态

| 操作 | 未指定选项 | `--with-dedup` | `--without-dedup` |
| --- | --- | --- | --- |
| 新装 | 按推荐配置安装并启用 | 安装并启用 | 关闭 |
| 旧版升级，无去重设置 | 按推荐配置安装并启用 | 安装并启用 | 保存显式关闭状态 |
| 已有去重设置 / 升级 | 保留保存状态与参数 | 安装、校验并启用 | 撤销接入并停用 |

两种选项同时出现直接报错。只有完成整项事务后才保存新的启用状态。重复指定当前状态不会生成新凭据或重置参数。

“没有设置”和“明确关闭”区别保存。在 `server.env` 记录 `ANYTLS_DEDUP_ENABLED=1/0`：缺少字段的旧版按新默认值迁移，`0` 则持续保持关闭。已有 `ANYTLS_DEDUP_BACKEND` 却没有受管状态的自定义部署不能被默认覆盖，需要明确迁移，避免接错解码端。

安装摘要明确区分“解码服务已就绪”和“客户端已实际去重”；首次安装不会声称已有压缩收益。

首版只增加上述两个用户参数。域名和资源参数放在受管配置中，向导显示推荐值；以后确有需求再增加单项 CLI 覆盖。

## 推荐配置

| 项目 | 推荐值 / 行为 |
| --- | --- |
| 程序 | `/usr/local/bin/anytls-dedup`，由同提交的 `./cmd/dedup` 构建 |
| 服务 | `anytls-dedup.service`，独立于 `anytls-server.service` |
| 配置 | `/etc/anytls/dedup.env`，root 所有，受管服务组可读，`0640` |
| 运行身份 | 独立系统用户 `anytls-dedup`，组使用主服务的受管组 |
| 数据入口 | `unix:/run/anytls-dedup/back.sock` |
| 统计入口 | `unix:/run/anytls-dedup/admin.sock` |
| 运行目录 | systemd `RuntimeDirectory=anytls-dedup`，权限 `0750` |
| socket 权限 | `UMask=0007`，只允许运行用户和受管组访问 |
| 允许域名 | `chatgpt.com,api.openai.com`，含子域名 |
| 缓存 | `256 MiB` |
| 在途预算 | `64 MiB` |
| 最大去重正文 | `64 MiB`；具体是否去重还受在途预算约束 |
| Go 软内存上限 | `448 MiB`，即当前 `256 × 1.25 + 64 + 64` 默认公式 |
| 服务硬内存上限 | systemd `MemoryMax=500M`，验收时读取实际 cgroup 限值 |
| 恢复 | `Restart=on-failure`、`RestartSec=1`；正常维护执行显式 restart |
| 退出 | 解码器排空 `30s`，systemd 停止超时 `40s` |
| 缓存持久化 | 不落盘，重启后由协议处理缓存冷启动 |

这些是当前缓存规模对应的固定推荐值，不自动按机器内存扩大缓存。预检展示主机内存、现有服务及新增上限，资源明显不足时明确失败；首版不承诺小内存服务器的自动调参。硬上限只约束解码服务，不能把 AnyTLS 主服务纳入同一受限 cgroup。

主服务的 `server.env` 增加 `ANYTLS_DEDUP_BACKEND='unix:/run/anytls-dedup/back.sock'`，使用现有程序的环境变量入口。普通 AnyTLS 密码、监听地址、fallback、padding 与客户端 URI 继续沿用已有值。

域名必须非空且使用现有域名解析规则校验；不能因为配置遗漏而退回允许任意域名。生产安装不开放测试用 `-resolve` 和 `-upstream-ca`。客户端 CA 由路由器前端管理，服务器只使用系统 CA 校验 HTTPS origin。

数据和统计均使用本机 Unix socket，不需要新增防火墙规则。socket 路径由安装器固定管理，启动前校验目录所有权、权限以及路径类型；`bind` 只替换同 UID 的 socket，拒绝删除普通文件、目录、符号链接或其他 UID 的 socket。

服务使用专用身份和现有主服务同级的 systemd 沙箱，仅允许写运行目录。主服务可用 `Wants=`、`After=` 提供开机启动顺序；不使用 `Requires=`、`BindsTo=` 或 `PartOf=` 将解码故障、停止或重启传播到主服务。所有真实就绪判定由健康检查完成。

## 安装、升级和回滚

1. 获取现有部署锁，校验仓库来源、分支及工作区，解析保存状态和本次选项。
2. 获取候选提交，在 staging 构建主程序、探针和需要的解码程序；先运行相关测试、配置校验和 systemd unit 校验。确认自带 `--binary` 支持去重；不支持时在切换前失败。
3. 备份主程序、探针、解码程序、配置、unit、受管用户标记、目录权限、两个服务的运行和自启状态。发现自定义 systemd drop-in 时在预检阶段拒绝部署，需先人工迁移。备份完整后才允许修改目标部署。
4. 原子安装候选文件。开启时先启动解码端并验证健康，再切换主服务接入；检查 socket 可由主服务身份访问。普通代理连接在主服务切换时会短暂中断。
5. 运行普通 AnyTLS 数据往返探针，再经实际 AnyTLS 通道访问 `dedup.anytls.arpa/health`；要求 HTTP `204` 且存在有效 `X-Edge-Dedup-Epoch`，并与本机解码端健康检查一致。
6. 关闭时先应用撤销后端的主服务配置并验证普通代理，再停止、禁用解码端。关闭后的保留配置不参与开机启动。
7. 两端检查成功后快进主源码目录，提交服务事务；源码推进失败也恢复旧部署。

任一步失败，恢复上述文件、权限和两个服务的原状态；首次安装失败要撤销本次新建的组件与身份。不能将“解码端安装失败但普通代理正常”作为整项启用成功。回滚失败保留备份目录并报告具体恢复失败项。

解码端运行中崩溃与安装失败分别处理：主服务继续运行，前端按现有协议暂停去重、走原路径并继续探测，解码端由 systemd 恢复。不能承诺故障瞬间的每个在途请求都无损；正文和流式请求的实际行为纳入故障验收。

## 旧安装器迁移

旧 bootstrap 对已有源码目录只 fetch，随后仍执行旧目录中的安装器。旧安装器会拒绝 `--with-dedup`；即使不传新参数，其升级流程也会由旧版函数提交 staging，无法完整应用新版默认组件。

最新 bootstrap 在取得同一部署锁后执行候选版本的事务协调器，显式传递“主源码目录”和“候选源码目录”，由新版协调器负责双服务备份、部署、验证及源码快进。无参数和显式 `menu` 都由下载的 bootstrap 展示管理菜单，只有选择安装或升级才 fetch 并执行候选安装器；状态、自检、重启和卸载继续使用本机入口。不要先 `git pull` 推进主源码目录再尝试安装。

协调器必须区分 Git worktree 中的 `.git` 文件与普通 checkout 的 `.git` 目录；更新期间所有源码与状态检查针对正确目录。重复 fetch、嵌套部署锁与递归候选测试需要沿用现有防护。

不能仅靠给旧 `do_update` 补传新参数完成迁移，也不能先更新主服务再在主事务外补装解码端。新装、已有旧版升级、已有新版更新和菜单动作最终使用同一个新版协调器。

## 自检与状态

继续使用现有 `status`、`doctor` 和 `uninstall`，不要求用户记第二个维护脚本。

`status` 展示：保存的开关、解码服务运行/自启状态、域名列表、有效资源限制、缓存及帧统计；统计不可达时标明原因，不能显示成零收益或健康。

`doctor` 分层检查：

- 普通代理：已有 TLS、认证、开流及正文往返探针。
- 解码安装：程序能力、配置、身份、unit、socket 权限和实际内存限制。
- 解码链路：本地健康检查和经 AnyTLS 的保留目标探测，校验状态码与 epoch。

隔离功能回归另用允许域名内的合成 HTTPS origin，检查重复正文还原与完整流式响应；不属于生产 `doctor` 的动作。

关闭状态跳过“解码服务必须运行”，同时检查主服务没有残留后端接入；启用状态的解码检查失败必须返回非零。生产端 doctor 不创建路由器 CA、不改变客户端设备名单、不执行真实 OpenAI 业务请求。

完整卸载先停止主服务使用组件，再停止解码服务，删除受管文件和安装器拥有的身份；不能误删复用的主服务组、用户自建文件或其他服务。失败时保留可恢复配置并返回非零。

## 验收与发布

已运行的本地检查及范围见 [当前状态](./status.md)。以下是验收要求，未记录为通过的项目仍需在对应环境验证。

在隔离安装测试里增加：新装默认开启、新装显式关闭、旧版本经 bootstrap 默认开启、旧版升级显式关闭、保存状态后的普通升级、明确关闭后升级保持关闭、缺失设置与零值的区别、自定义后端迁移冲突、重复开启、显式关闭、完整卸载、互斥选项及非法配置。

故障注入覆盖：解码构建/启动/健康失败、socket 权限或路径冲突、主服务切换失败、数据往返失败、解码链路失败、源码快进失败、退出信号、双服务原本独立运行/停止与自启组合，以及回滚本身失败。全部核对文件内容、服务状态和残留身份。

真实 systemd 隔离环境补验：500 MiB 硬上限、解码器崩溃自恢复、重启后缓存冷启动、解码故障不连带停止主服务、同一 AnyTLS 连接上的普通与去重流量、并发请求和完整流式响应。模拟 systemctl 测试不能替代这些验收。

发布顺序：合入安装器与 bootstrap 迁移实现 → 通过上述验证 → 发布包含去重代码的同一版本 → 才对生产机执行启用命令。`69.63.200.32` 上确认普通代理和解码链路后，再在既有 `192.168.6.229` 灰度范围验证 CA、真实业务和前后端统计。

最终报告分别给出“安装正常”“路由器已发现解码端”“业务成功”“观察到实际去重收益”，每一项都需要独立证据。
